> **说明**：本文描述 FrontPost 的方法论与目标架构，涉及的模型训练、排序策略和系统组件属于设计设想，**不代表当前已经部署或验证的线上能力**。
{: .notice--info }

FrontPost 的长期目标，是把来源发现、证据审查、研究解释、个性化编排与持续反馈连接成一个面向长期信息价值的学习系统。它不只是给候选内容打分的推荐器，而是一套从“世界发生了什么”到“什么值得这个人现在知道”，再到“这次选择是否真的帮到他”的端到端研究框架。搜索、AI 问答、论文阅读、公开邮报和个人推荐可以共享内容对象、Conversation、Run 与 Delivery 等基础语义。

## 内容如何产生

FrontPost 每天围绕六个公开大领域和二十二个细分领域生成两类内容：

- `News`：研究动态、产品发布、数据集、标准、政策及其他可核实的新变化。
- `Paper`：围绕单篇或一组论文生成的研究解读。

每份内容保存为对象存储中的独立 Markdown。一次整理可以生成多份 Markdown，并由一个 `Edition` manifest 记录顺序、摘要和内容哈希。PostgreSQL 只保存对象 key、哈希和状态索引，不保存论文关系图谱。Web、Email、RSS、MCP 和 Zotero 从同一组 Markdown 与 manifest 渲染。

公共内容按日期、领域、细分领域和语言组织：

```text
public/{date}/{field}/{subfield}/{document_id}/{locale}.md
```

同一个内容 ID 分别保存中文、英文、阿拉伯文等语言文件。产品展示滚动最近七天目录，底层文件继续按自然日期归档。

## 公共内容与个人内容

公共自动任务持续维护六个领域的内容池。每个细分领域分别生成 News 和 Paper。公共首页在最近七天范围内按全局质量选择内容，并应用领域配额、内容哈希去重和来源多样性约束。首页不计算个人相关性。

个人任务先检索最近七天公共内容，再根据用户显式编写的 Focus 执行专项搜索。系统合并两组候选、去重和排序，对公共目录尚未覆盖的候选生成个人 Markdown，并用公共高质量内容补齐用户要求的 News/Paper 数量。

公共 Markdown 进入个人工作区时保持内容哈希不变。个人 Edition 通过内容地址引用完成虚拟复制；导出工作区时再生成文件副本。公共内容不根据个人阅读历史或收藏改写。

个人任务发现具有公共价值的新内容对象时，公共 Worker 会移除 Focus、Conversation memory、收藏和阅读历史等用户上下文，再按公共模板生成多语言 Markdown。

## 面向长期信息价值的端到端学习架构

推荐问题被表述为一个跨越内容、用户与时间的联合推断任务：在给定用户当前意图和历史状态的条件下，系统需要判断一条信息是否可信、是否值得关注、现在是否仍然及时，以及将它放进整期内容后是否能改善用户未来的理解与回访。单一分类器或静态加权公式无法覆盖这些互相制约的目标。目标架构因此由证据表征、长期用户建模、多任务概率预测、列表决策和持续研究五个部分组成，并以一条端到端训练与评估闭环贯通。

### 证据表征：从文档表示走向可追溯主张

训练样本的基本单位不止是“文章—标签”，还包括主张、来源、段落、研究方法、数据集、时间和相互引用关系。模型可以将这些材料组织成带类型和时间戳的证据网络：每个结论都能回到支持、限定或反驳它的原文位置；每个来源都保留发布者、版本、许可和可核验状态。跨来源重复报道不被误当成独立验证，引用关系也不会自动等价为证据支持。

在此基础上，研究内容编码器联合学习领域语义与证据关系表示。对论文，可吸收摘要、正文、图表说明、方法和补充材料；对新闻和产品变化，则关注原始公告、版本差异、数据与时间线。文本、多语言版本、表格和代码变更可以映射到共享语义空间，再由领域专家模块捕捉不同学科的术语、证据标准与信息密度。来源冲突、缺失和分布外内容作为模型输入和不确定性来源保留下来，而不是被归并成一个看似精确的“质量分”。

质量评估采用分层概率模型，输出研究重要性、方法严谨性、证据充分性、可复现性和信息增量等维度的联合分布。系统关注的不只是后验均值，还包括区间宽度、维度间冲突和证据覆盖率；低置信度应导致谨慎排序、补充检索或复核，而非让模型以流畅的解释掩盖资料不足。期刊名次、引用数、机构声誉、社交热度和 GitHub star 仅作为经过校准且影响受限的辅助特征，不能替代对论证本身的分析。

### 长期用户模型：让兴趣拥有时间尺度

用户状态不是静态标签，而是一段会变化、也会遗忘的个人信息轨迹。模型将它拆解为三个相互作用的层次：稳定的长期领域兴趣、由 Focus 和 Conversation 表达的阶段性任务、以及本次阅读会话的即时意图。显式关注和排除条件构成高置信度控制信号；打开、有效阅读、收藏、追问、标记有用或无关、快速跳过和后续回访则以不同语义进入事件序列。

序列模型利用事件顺序、间隔、上下文和内容表示来估计兴趣状态转移，不把“未点击”简单等同于“不喜欢”。曝光位置、候选供给、阅读时长截尾、反馈延迟和用户暂时离开都会造成观测偏差，需要通过曝光建模、倾向校正、删失分析和显式反馈交叉校准。用户兴趣在不同时间尺度上分别更新：短期任务可以迅速变化，长期偏好则需要重复证据才更新。对新主题保留受控探索空间，避免历史点击把信息范围锁死。

### 联合表征与概率预测：从反馈事件到用户价值

在线服务可以保留候选生成和精排的计算边界，训练目标则共享上游表征并联合校准。候选生成层面向覆盖率与召回率，从多领域语料和新近来源中找到语义相关、证据结构互补的内容；精排层将候选、证据状态、用户长短期表征、时间上下文和当前列表状态共同编码，再输出彼此校准的多个概率结果。研究路线也应评估生成式召回与精排在统一用户序列模型中的联合训练：模型根据不同结果目标生成候选，再由证据约束的列表决策器编排整期内容。其核心可抽象为：

```text
p(证据质量, 个人相关性, 有效阅读, 正向反馈, 负向反馈, 后续回访
  | 内容与证据, 用户历史, 当前任务, 时间上下文)
```

共享主干通过跨领域迁移学习共性，领域专家和任务专属预测头保留科学子领域、News/Paper 类型及不同用户反馈的差异。模型既预测即时结果，也建模延迟结果；短期点击只是一项弱反馈，完成阅读、收藏、主动追问、明确纠错和跨周期回访提供不同强度的监督。经偏差校正的隐式事件、用户明确表达和可审计的专家判断共同组成训练信号，模型同时学习不确定性和校准误差。

整期邮报由列表级决策器生成。它评估候选之间的边际价值、主题覆盖、来源独立性、重复程度和时效衰减，并在质量可信度底线之上平衡信息增量、个人相关性与适度探索。目标函数面向一段时间内的有效阅读和持续回访，而不是把用户压缩成点击概率。概念上，策略优化可表述为在证据风险约束下最大化长期效用：

```text
π* = argmaxπ E[Σ(t=0…H) γ^t · 用户价值(t) | π]
约束：候选的证据风险、来源集中度和过期曝光率不超过可接受边界
```

其中长期回报需要按成熟队列观察，并与即时反馈分别估计。由于回访稀疏、延迟且难以归因，模型还可以学习一组较早可观测、并经队列验证与未来留存相关的下游奖励信号，再将它们用于不同排序任务的策略优化；这些代理奖励需定期检查与长期结果的校准关系，不能替代真实留存。对延迟回报的优化先从离线轨迹、反事实评估和保守策略学习开始；只有在估计稳定、护栏有效时，才通过小流量受控实验检验策略变化。这样的次序避免把不稳定的离线强化学习结果直接当作真实用户价值。

### 统一训练：由数据基础模型逐步走向策略模型

完整训练路线不是一次性训练一个更大的排序网络，而是逐步形成互相校验的模型族与任务体系：

1. **领域与证据预训练**：在获得许可的公开语料及合规内容上，进行多语言对比学习、主张—证据对齐、来源版本识别、跨文档关系建模和时间顺序预测，得到可迁移的内容与证据表征。
2. **长期行为预训练**：以带时间间隔的用户事件序列为对象，学习下一事件、兴趣状态变化、阅读深度及跨领域迁移；使用掩码事件、序列对比和跨时间切分任务，避免只在短会话、单一领域中学会猜下一次点击。
3. **专家监督与偏好对齐**：把可审计的研究评估、用户显式偏好、纠错记录和经过曝光偏差处理的行为信号组合起来，对概率头进行多任务校准和偏好优化。冲突标签保留其来源和分歧，不以简单多数投票消除异议。
4. **端到端列表训练**：联合微调内容编码、证据交互、用户状态和排序模块，使局部信号最终服务于整期内容的效用；质量后验作为选择约束参与决策，不与用户偏好混成一个不可解释的单一分数。
5. **策略蒸馏与在线适配**：经离线策略比较和反事实检查后，将稳定策略压缩到低延迟召回与排序模型；在线只更新可验证的用户状态和安全的轻量参数，较大模型及奖励函数则通过版本化训练周期演进。

这条路线的规模研究需要同时考察数据质量、模型容量、序列长度、专家数量、计算量、延迟和能源成本，建立可重复的性能—计算曲线。若训练数据、授权范围和实际业务规模逐步成熟，可以探索共享基础模型、稀疏专家、长序列注意力、检索增强和领域小模型协作。大规模预训练阶段将评估跨节点加速器集群、数据/张量/参数并行、优化器状态分片、混合精度和异步特征刷新；服务阶段再通过蒸馏与缓存把研究模型转化为可控的低延迟召回和排序能力。参数规模不是研究成果本身；要证明额外算力是否带来可信度、跨域泛化、留存或时效的可测增益。

### 持续演进：快速研究环与长期验证环

模型演进将采用两个速度不同、互相制约的闭环。**快速离线环**由研究智能体提出可检验假设、分析失败样本、生成特征或损失函数候选，并在固定数据切分、版本化语料和资源预算内执行高通量实验。实验记录假设、代码、数据快照、模型版本、随机种子、计算成本与失败原因；代理可自动提出和筛选方案，但不能用同一批验证数据反复调参后仍把它称作独立泛化证据。

**慢速业务环**通过影子流量、分层随机实验和长期队列比较，检验离线候选是否改善 D7/D28 留存、有效阅读和明确反馈，同时监视证据质量、来源多样性、纠错率、延迟、成本和不同用户群体之间的差异。只对通过统计检验与护栏审查的版本逐步扩大实验范围；效果回退时可回滚至已知稳定策略。模型、数据、奖励函数和评估器都要版本化，避免评价标准随模型变化而悄悄放宽。

### 业务目标与研究评价

FrontPost 的业务优化以用户是否持续获得可信且及时的信息价值为主线。具体指标先作为目标评估框架定义，再依据真实用户和产品形态校准口径：

| 目标 | 建议观察的指标 | 需要共同检查的护栏 |
| --- | --- | --- |
| 持续使用与留存 | 固定队列口径下的 D7/D28 留存率、回访间隔、留存用户的有效阅读会话数 | 新老用户分层、渠道差异、退订和长期沉默 |
| 反馈与满意度 | 每次有效曝光对应的收藏/有用反馈率、阅读完成度、主动追问率、明确负反馈与纠错率 | 不把沉默或未点击直接视为负反馈，校正位置和候选供给偏差 |
| 信息及时程度 | 来源发布至首次发现、核验完成和用户收到的分段时延 P50/P90；主题条件化的过期曝光率 | 重要事实核验完整度、来源可靠性、纠错与撤回时延 |
| 信息质量与覆盖 | 证据覆盖、概率校准误差、来源独立性、主题/领域覆盖和新颖内容发现率 | 低置信内容曝光、来源集中、重复率和群体质量差异 |
| 系统效率 | 每个有效阅读会话的推理成本、端到端投递延迟、模型与数据刷新成本 | 不能用降低来源核验、压缩必要上下文或牺牲弱势领域覆盖换取效率 |

时效应按主题生命周期建模：突发政策和版本变化可能迅速衰减，基础方法和经典研究则可长期有用。信息进入排序前必须经过来源和证据门槛；时间衰减只决定何时优先展示，不决定事实是否成立。评估按领域、News/Paper、语言、用户生命周期和分发渠道拆分，并同时使用时间外推、跨域测试、未见用户测试、校准曲线和小流量实验。

研究评估以科研质量的可解释维度为锚点，参考 [NIH 对重要性、严谨性与可行性的定义](https://www.grants.nih.gov/policy-and-compliance/policy-topics/peer-review/simplifying-review/framework)、[PLOS 可复现性共识](https://journals.plos.org/plosbiology/article?id=10.1371%2Fjournal.pbio.3003726)、[TOP 透明度规范](https://www.cos.io/initiatives/top-guidelines)和 [DORA 指标使用原则](https://sfdora.org/resource/guidance-on-the-responsible-use-of-quantitative-indicators-in-research-assessment/)。对 AI 评审的表面操纵风险，也需纳入红队数据和压力测试，参见 [Gaming AI-Assisted Peer Reviews Poses New Risks](https://arxiv.org/abs/2606.10159)。模型必须能指出“为什么相信、依据在哪里、哪里仍不知道”，而不是只给一个漂亮的总分。

这套研究路线吸收并重新组合了近期公开工作中的几条重要方向：[PinFM](https://arxiv.org/abs/2507.12704)展示了预训练长期用户行为序列基础模型的路径；[HORIZON](https://aclanthology.org/2026.findings-acl.1503/)把评估扩展到跨时间、跨领域和未见用户，提示单步 next-item 命中率不足以代表真实用户建模；[UniMixer](https://arxiv.org/abs/2604.00590)研究推荐架构的统一设计和规模规律；[UniPinRec](https://arxiv.org/abs/2606.00422)探索将生成式召回和精排纳入同一模型、训练和服务链路；Pinterest 的[长期用户价值下游奖励学习](https://arxiv.org/abs/2607.14192)研究如何从较早的会话行为中提取可用于长期留存优化的奖励信号；Google 的 [Self-Evolving Recommendation System](https://research.google/pubs/self-evolving-recommendation-system-end-to-end-autonomous-model-optimization-with-llm-agents/)则提出由高速离线研究环和延迟业务指标验证环组成的自动演进流程。FrontPost 将这些方向作为研究起点，进一步把科学证据图、时间敏感的信息价值、长期用户效用和可审计的模型迭代放入同一个端到端问题中。它们是可持续验证的研究假设，不是已完成的能力声明。

## Conversation、Run 与自动投递

`Conversation` 保存连续消息、记忆摘要、关联 Focus 和多个 Run。用户提问、继续追问、点击“立即整理”和定时任务都在 Conversation 下创建 Run。

每个自动 Focus 关联一个长期 Conversation。每次定时触发创建独立 Run，记录输入快照、Skill 版本、checkpoint、成本、输出 URI 和状态。Skill context 依次装配 Focus、Conversation memory、当前触发参数、阅读反馈摘要、公共候选和外部来源。显式 Focus 拥有最高优先级。

PostgreSQL 保存时区、目标发送时间、频率、提前量、下一次触发时间和幂等键。Scheduler 使用数据库行锁抢占到期规则，按 `schedule_id + scheduled_for` 创建唯一 Run，再把任务写入 Redis。

生成任务根据历史耗时提前启动。同一发送时间的大批任务按稳定散列分布到提前窗口。临近截止时间时，Run 停止扩大搜索范围，使用已验证结果和公共内容补齐。Edition manifest 完成后才创建 Delivery。

初始 Worker 分为两个独立队列：

- `interactive`：至少五个副本，处理实时提问和立即整理。
- `scheduled`：至少五个副本，处理公共采编、个人定时整理和投递。

| 产品与交付 | Web、Expo、Reader、Search、Ask、Email、RSS、MCP、Zotero | 用户输入、内容呈现与渠道适配 |
| 产品服务与任务编排 | Better Auth、FastAPI、assistant-ui、DeepAgent/LangGraph、Skills、Scheduler、TaskIQ | 身份、领域 API、Conversation/Run 和任务执行 |
| 内容生产 | 来源、内容校验、质量评估、公共池、个人检索、Markdown、Edition | 生成和复用 News/Paper |
| 数据基础设施 | PostgreSQL、对象存储、Redis | 持久状态、内容工件与 Worker 队列 |

PostgreSQL 保存业务状态、Conversation/Run、定时规则、评分索引、Edition 索引和 Delivery。对象存储保存来源快照、Markdown、运行工件和 manifest。Redis 主要提供 TaskIQ 队列、任务结果、短锁和临时缓存。

## 八个核心对象

![FrontPost 核心领域对象](/images/2026/frontpost-methodology/frontpost-core-objects.svg)

- `User / Profile`：身份、语言、权限、阅读和投递偏好。
- `Focus`：研究范围、排除项、数量、语言、时序和渠道配置。
- `Conversation`：连续消息、长期记忆和多个 Run 的上下文容器。
- `Run`：一次交互、立即整理或定时执行及其状态与工件。
- `ContentDocument`：对象存储中的一份 News/Paper Markdown 及语言变体；数据库只保存 object key、哈希和状态索引。
- `Edition`：一次 Run 产生的文档清单、顺序和摘要 manifest。
- `Delivery`：接收者、渠道、状态、幂等键和实际内容哈希。

```text
User → Focus → Conversation → Run
Run → Markdown ContentDocument
Run → Edition ↔ ContentDocument
Edition → Delivery
```

来源记录、引用轨迹、质量评估、Schedule 和反馈事件作为上述对象的结构化子记录或运行数据保存。

## 一致交付

Run 完成内容整理后直接写入 Edition manifest。重新整理会产生新的 Run 和 Edition ID。历史 Delivery 继续引用原 manifest。

Delivery 使用 `edition_id + recipient_or_feed + channel` 作为幂等键。渠道只渲染 manifest 指向的 Markdown，不重新排序或生成内容。阅读、收藏、完成、跳过、不相关和退订用于下一次相关性排序与 Conversation memory，不修改已经发送的 ContentDocument。
